## Simulator and policy as Flows

The Lift task is a feedback loop: the environment produces a `LiftState`, the
policy consumes it and returns a `LiftAction`, which feeds back into the
environment. `LiftEnvFlow` runs a deterministic mock so the smoke test needs no
robosuite install.

```python
from retriever.flow import Flow, Latest, Pipeline, Rate, Trigger, io

@io
class LiftAction:
    dz: float | None = None
    grip: float | None = None

@io
class LiftState:
    step: int | None = None
    source: str | None = None
    object_height: float | None = None
    gripper_z: float | None = None
    reward: float | None = None
    done: bool | None = None

class LiftEnvFlow(Flow[LiftAction, LiftState]):
    """robosuite Lift, or a deterministic mock when robosuite is absent."""
    def step(self, action: LiftAction | None) -> LiftState:
        self.step_idx += 1
        dz   = 0.0 if action is None or action.dz   is None else float(action.dz)
        grip = -1.0 if action is None or action.grip is None else float(action.grip)
        return self._step_mock(dz=dz, grip=grip)   # or _step_robosuite in real mode

class HeuristicLiftPolicy(Flow[LiftState, LiftAction]):
    """Approach, close the gripper, then lift."""
    def step(self, state: LiftState | None) -> LiftAction:
        if state is None or state.object_height is None:
            return LiftAction(dz=-0.4, grip=-1.0)
        if state.object_height >= self.target_height:
            return LiftAction(dz=0.0, grip=1.0)
        if state.gripper_z > state.object_height + 0.06:
            return LiftAction(dz=-0.5, grip=-1.0)
        if state.gripper_z > state.object_height + 0.005:
            return LiftAction(dz=-0.2, grip=-1.0)
        return LiftAction(dz=1.0, grip=1.0)
```

The feedback edge is explicit: `env → policy` and `policy → env`. The environment
ticks at `env_hz`, the policy at `policy_hz`, and the printer wakes on each new
`step`.

```python
pipe = Pipeline("robosuite_lift_demo")
with pipe:
    env     = LiftEnvFlow(mode="mock", ...)          @ Rate(hz=20)
    policy  = HeuristicLiftPolicy(target_height=1.05) @ Rate(hz=5)
    printer = LiftPrinter(print_every=2)              @ Trigger("step")
    pipe.connect(env, policy, sync=Latest())
    pipe.connect(policy, env, sync=Latest())          # feedback loop
    pipe.connect(env, printer, sync=Latest())
```

## Connect Retriever to RoboCasa

The Retriever Embodied Demo Console makes the simulator boundary concrete. Its
offline-first path needs no model credentials:

```text
Goal -> Planner -> Skill plan -> Recorded replay -> Task verification
```

The full Flow remains inspectable:

```bash
pixi run demo-robocasa-mock
```

```text
GoalSource -> EmbodiedPlanner -> SkillDispatcher -> DemoActionSource
                                                        |
                                                      Latest
                                                        v
                         EventSink <- TaskVerifier <- RoboCasaSimulator
```

RoboCasa owns tasks, demonstrations, and success signals. RoboSuite composes
the environment and controller. Demonstration mode restores recorded states;
action-replay mode advances MuJoCo. Retriever owns goals, plans, dispatch,
controls, events, and verification. Retriever's standalone
web console embeds mjviser as a replaceable viewport; mjviser only renders the
same live `MjModel` and `MjData` in the browser.

Follow the [locked setup and data steps](https://github.com/openretriever/golden-retriever/tree/main/examples/advanced/robocasa#install-the-simulator-environment),
then run the replay:

```bash
pixi run --locked -e robocasa demo-robocasa-replay
```

Environment construction completes before the requested replay duration begins.
The first MJCF and asset initialization can still take roughly 15 seconds on a
laptop.

Use `pixi run --locked -e robocasa demo-robocasa-rerun` for MuJoCo camera frames plus
Retriever telemetry. Only the optional passive native viewer requires
`mjpython`, and only on macOS; browser and headless modes use ordinary Python.

Remote workers can add `--rerun-mode record --recording <path>.rrd` to save the
same trace without spawning a viewer, then inspect it later on a local machine.
This uses Retriever's deterministic step recorder and stops after the final
recorded action unless `--repeat` is set.

### Live browser replay

This is the shortest visual proof that Retriever is connected to a real
manipulation stack: recorded data passes through typed Flows, RoboCasa
evaluates the task, and the browser shows the same in-process simulator state.
The viewer is not a separate animation.

Start the scene launcher, then open `http://localhost:8084`:

```bash
pixi run --locked -e robocasa demo-robocasa-scenes
```

The launcher lists downloaded human demonstrations and starts one simulator at
a time. Choose **Retriever console** to open `http://localhost:8086` with the
mjviser renderer embedded from `http://localhost:8085`, or **Viser native** for
the original dockable local-debug workspace. Curated entries include atomic
tasks (`CoffeeSetupMug`, `StartCoffeeMachine`, `TurnOnMicrowave`) and composite
tasks (`PrepareCoffee`, `PackIdenticalLunches`, `LoadDishwasher`,
`OrganizeCondiments`, `StackBowlsCabinet`, `RestockPantry`). Other compatible
installed datasets remain selectable. Unavailable datasets stay visible with a
setup reason. `CoffeeSetupMug` is the initial atomic pick-place example and
`PrepareCoffee` is the installed composite reference run. Task switching lives
here because each selection replaces the RoboCasa environment, demonstration,
and MuJoCo model.

### Execution modes and composite plans

The current public example executes **demonstrated trajectory replay**, which
is available now. The offline or optional Gemini planner produces an
allow-listed `SkillPlan`, but `DemoActionSource` supplies recorded states and
actions from the selected RoboCasa demonstration. Choosing Gemini therefore
changes the proposed plan structure; it does not turn the replay into a live
model-generated trajectory.

Composite manifests organize that plan into ordered **subplans**, with one or
more dependency-ordered **skills** inside each subplan. The dashboard advances
both levels using curated normalized-progress annotations and preserves passed
items alongside the current phase. Those phase boundaries are readable replay
annotations, not independently detected skill-completion events. RoboCasa
reward and success remain the explicit final verifier.
For `PrepareCoffee`, the subplans are inspect workspace, position the mug, brew
coffee, and verify outcome. The curated catalog also names genuine RoboCasa
composites such as `PackIdenticalLunches`, `LoadDishwasher`,
`OrganizeCondiments`, `StackBowlsCabinet`, and `RestockPantry`. These entries
remain visible when their datasets are absent, with the missing requirement
shown explicitly instead of allowing a launch that will fail.

**Dynamic planner execution is an extension point.** A policy, DMP, TAMP executor,
or remote planner can replace `DemoActionSource` while preserving the typed
simulator, event, console, and verification boundaries. The interfaces are
ready for that integration, but the current public demo does not claim that
this low-level live-control path is implemented.

The left Retriever panel is a standalone experiment console, not a Viser
overlay. It communicates with Retriever through a small JSON API and treats the
renderer as an iframe URL, so another local or remote renderer can replace
mjviser without changing planning or experiment controls.
**Run** controls the recorded replay Flow and reports current progress, reward,
success, and the dataset action norm from `RoboCasaObservation`. **Plan** shows ordered
subplans and advances their nested skills with the trajectory. **Graph** shows
the seven typed Retriever stages, and **Events** gives a compact execution and
verification log. Run also provides a compact planner conversation for text
goals, planner selection, plan acceptance, and the final verified result. The
transcript is derived from the same typed Retriever state and events rather
than owning a parallel command path. The embedded viewport remains dedicated to mjviser's scene
controls. Use the console **Camera** control for agent-facing, tracked robot,
and overhead views; disable **Track camera** inside the viewport for a static
world frame. The optional `--native-viser-controls` panel remains a supported
Viser-native frontend over the same Retriever state; the standalone console is
the renderer-independent boundary for portable and remote use.

The launcher is the task-level entry point. Each viewer remains bound to one
task and keeps the run controls, camera presets, and pipeline map close to the
simulator state they affect.

The locked simulator environment includes the optional Gemini client. Set
`GEMINI_API_KEY` to request structured, allow-listed skills. The planner cannot
execute code or issue arbitrary MuJoCo actions; when credentials are absent or
an operational request fails, the console receives and labels an
`offline`-sourced fallback plan.

The recorded action source is intentionally replaceable. A learned policy,
planner, or memory-backed skill system can emit the same `RoboCasaAction`
payload without changing the simulator Flow. The existing
[`openpi_policy`](https://github.com/openretriever/golden-retriever/tree/main/examples/advanced/openpi_policy)
lane already owns GoldenRetriever's `PolicyObservation -> ActionChunk`
contract; future policy wiring should add a small action-chunk adapter instead
of defining another policy interface. See the full setup and expected output
in [`examples/advanced/robocasa/README.md`](https://github.com/openretriever/golden-retriever/tree/main/examples/advanced/robocasa).

## Run these in order

Run the simulator lanes from lightest to heaviest so each boundary is verified
before the next:

1. **Mock robosuite** — `pixi run demo-robosuite-mock` runs the env↔policy loop deterministically, without a robosuite install.
2. **Mock RoboCasa contract** — `pixi run demo-robocasa-mock` verifies the recorded-action → simulator → observation graph without RoboCasa.
3. **Locked simulator smoke** — `pixi run --locked -e robocasa robocasa-smoke` imports the stack and constructs headless `Lift`.
4. **Real RoboCasa replay** — `pixi run --locked -e robocasa demo-robocasa-replay` replays the downloaded demonstration.
5. **Atomic and composite verification** — after downloading `CoffeeSetupMug` and `PrepareCoffee`, `pixi run --locked -e robocasa test-robocasa-replay-data` requires both recorded episodes to reach RoboCasa success.

## Design notes

Making the environment and policy ordinary Flows keeps timing and handoffs
visible instead of hiding them in callbacks. The same typed simulator boundary
runs against either a mock or a real backend, while Retriever recording and
Rerun expose observations without changing the policy contract.

GoldenRetriever owns the Flow adapter, dependency lock, runnable examples, and
public documentation. Large assets, datasets, recordings, and machine-specific
caches remain outside version control so the repository and Hub manifest stay
lightweight.

RoboCasa supplies tasks and demonstrations, robosuite composes environments
and controllers, demonstration mode restores recorded states, and action-replay
mode advances MuJoCo. Retriever orchestrates typed policy and simulator Flows,
and a replaceable renderer adapter projects that run into the view needed for
debugging.

The public console has no ROS or Isaac Sim dependency. It is tested
interactively on macOS; Linux is the intended headless target. WSL2 is
experimental and currently unverified.
