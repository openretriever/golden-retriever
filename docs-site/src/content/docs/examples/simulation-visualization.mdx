## Simulator and policy as Flows

The Lift task is a feedback loop: the environment produces a `LiftState`, the
policy consumes it and returns a `LiftAction`, which feeds back into the
environment. `LiftEnvFlow` runs a deterministic mock so the smoke test needs no
robosuite install.

```python
from retriever.flow import Flow, Latest, Pipeline, Rate, Trigger, io

@io
class LiftAction:
    dz: float | None = None
    grip: float | None = None

@io
class LiftState:
    step: int | None = None
    source: str | None = None
    object_height: float | None = None
    gripper_z: float | None = None
    reward: float | None = None
    done: bool | None = None

class LiftEnvFlow(Flow[LiftAction, LiftState]):
    """robosuite Lift, or a deterministic mock when robosuite is absent."""
    def step(self, action: LiftAction | None) -> LiftState:
        self.step_idx += 1
        dz   = 0.0 if action is None or action.dz   is None else float(action.dz)
        grip = 1.0 if action is None or action.grip is None else float(action.grip)
        return self._step_mock(dz=dz, grip=grip)   # or _step_robosuite in real mode

class HeuristicLiftPolicy(Flow[LiftState, LiftAction]):
    """Approach, close the gripper, then lift."""
    def step(self, state: LiftState | None) -> LiftAction:
        if state is None or state.object_height is None:
            return LiftAction(dz=-0.4, grip=1.0)
        if state.done or state.object_height >= self.target_height:
            return LiftAction(dz=0.0, grip=-1.0)
        if state.gripper_z > state.object_height + 0.08:
            return LiftAction(dz=-0.5, grip=1.0)
        return LiftAction(dz=0.6, grip=-1.0)
```

The feedback edge is explicit: `env → policy` and `policy → env`. The environment
ticks at `env_hz`, the policy at `policy_hz`, and the printer wakes on each new
`step`.

```python
pipe = Pipeline("robosuite_lift_demo")
with pipe:
    env     = LiftEnvFlow(mode="mock", ...)          @ Rate(hz=20)
    policy  = HeuristicLiftPolicy(target_height=1.05) @ Rate(hz=5)
    printer = LiftPrinter(print_every=2)              @ Trigger("step")
    pipe.connect(env, policy, sync=Latest())
    pipe.connect(policy, env, sync=Latest())          # feedback loop
    pipe.connect(env, printer, sync=Latest())
```


For a live browser scene, install `mjviser` in the configured simulation
environment and run `retriever run demo-robosuite-web`. The viewer consumes the
same native `MjModel` and `MjData` that robosuite advances; it does not launch a
second simulator.

## Connect Retriever to RoboCasa

The RoboCasa replay lane makes the simulator boundary concrete:

```bash
retriever run demo-robocasa-mock
```

```text
DemoActionSource @ 20 Hz
          |
        Latest
          v
RoboCasaSimulator @ 20 Hz ---> ObservationPrinter @ Trigger
```

After installing RoboCasa from source, downloading its kitchen assets, and
downloading the `TurnOnMicrowave` human demonstration, run real physics:

```bash
python -m examples.advanced.robocasa.app \
  --mode robocasa --task TurnOnMicrowave --seconds 45
```

The duration includes environment construction; leave startup budget for MJCF
and asset initialization in addition to the replay itself.

Add `--visualize rerun` for MuJoCo camera frames plus Retriever telemetry. On
macOS, use `mjpython ... --viewer` for the native MuJoCo viewer; native viewer
and offscreen camera modes remain separate because they create incompatible
AppKit/GLFW contexts in one process.

Remote workers can add `--rerun-mode record --recording <path>.rrd` to save the
same trace without spawning a viewer, then inspect it later on a local machine.
This uses Retriever's deterministic step recorder and stops after the final
recorded action unless `--repeat` is set.

### Live browser replay

This is the shortest visual proof that Retriever is driving a real manipulation
stack: recorded actions pass through typed Flows, RoboCasa evaluates the task,
MuJoCo advances physics, and the browser shows that exact live state. The
viewer is not a separate animation.

Run the composite kitchen demo, then open `http://localhost:8085`:

```bash
retriever run demo-robocasa-composite-web
```

The `PrepareCoffee` demonstration contains 749 controls and reaches RoboCasa
success at step 731. The same simulator Flow can later accept a learned policy,
memory-backed skill, or TAMP executor instead of the recorded action source.

The left **Retriever replay** panel is an experiment console, not a viewer-only
overlay. Pause or resume the recorded-action Flow, advance one action while
paused, restart the episode, or slow it down for inspection. Live progress,
reward, success, and action norm come from `RoboCasaObservation`. Open the
**Graph** tab for a live HTML node-and-edge view of the typed path from
`DemoActionSource` through `RoboCasaSimulator` to `ObservationPrinter`; the
right panel remains dedicated to mjviser's scene controls.

The recorded action source is intentionally replaceable. A learned policy,
planner, or memory-backed skill system can emit the same `RoboCasaAction`
payload without changing the simulator Flow. The existing
[`openpi_policy`](https://github.com/openretriever/golden-retriever/tree/main/examples/advanced/openpi_policy)
lane already owns GoldenRetriever's `PolicyObservation -> ActionChunk`
contract; future policy wiring should add a small action-chunk adapter instead
of defining another policy interface. See the full setup and expected output
in [`examples/advanced/robocasa/README.md`](https://github.com/openretriever/golden-retriever/tree/main/examples/advanced/robocasa).

## Run these in order

Run the simulator lanes from lightest to heaviest so each boundary is verified
before the next:

1. **Mock robosuite** — `retriever run demo-robosuite-mock` runs the env↔policy loop deterministically, without a robosuite install.
2. **Mock RoboCasa contract** — `retriever run demo-robocasa-mock` verifies the recorded-action → simulator → observation graph without RoboCasa.
3. **Real RoboCasa / Rerun** — replay a human demonstration through real RoboCasa physics after the mock trace looks right.
4. **Real robosuite / Rerun** — swap `mode="robosuite"` (optional dependency) only after the mock trace looks right.

## Design notes

Making the environment and policy ordinary Flows keeps timing and handoffs
visible instead of hiding them in callbacks. The same typed simulator boundary
runs against either a mock or a real backend, while Retriever recording and
Rerun expose observations without changing the policy contract.

The ownership boundary is deliberate. GoldenRetriever owns the Flow adapter,
examples, and public explanation. A external simulator environment owns Pixi locks, source
checkouts, large assets, datasets, and machine-specific run configuration.
This heavy stack is not exported from GoldenRetriever's current Hub manifest:
Hub loading must remain lightweight. Once the launcher and action/observation
contract are stable, a dedicated `openretriever/robocasa-demo` pack can expose
that narrow boundary without duplicating simulator code or assets.

RoboCasa supplies tasks and demonstrations, robosuite composes environments
and controllers, MuJoCo executes physics, Retriever orchestrates typed policy
and simulator Flows, and mjviser or Rerun projects that run into the view needed
for debugging. A future TAMP demo can replace `DemoActionSource` with planner
and executor Flows while preserving the simulator and visualization layers.
