    <p class="kicker">Robot payload selection</p>
    <h2>Choose by the handoff, not by the ontology.</h2>
    <p>Golden payloads are for reusable robot examples. Start from the boundary you need to preserve: a local spatial value, a stamped graph handoff, scene memory, planner intent, motion output, execution status, or replayable event record.</p>
  </div>
  <div class="reference-command">
    <p class="kicker">Run first</p>
    <pre><code>pixi run demo-robotics-typing-catalog</code></pre>
    <p>Expected result: representative spatial and robot-facing payloads are constructed, registry lookup succeeds, and validation prints a compact summary.</p>
  </div>
</div>

<div class="purpose-strip">
  <div><strong>Use the smallest reusable payload.</strong><p>Prefer a narrow type that preserves the boundary instead of a broad object that silently becomes a project-specific blob.</p></div>
  <div><strong>Stamp values before they cross boundaries.</strong><p>Add frame, event time, and source metadata before values enter replay, planning, control, export, or another process.</p></div>
  <div><strong>Keep optional integrations outside the base layer.</strong><p>Camera, simulator, model, robot, network, and private dataset details should not be required to import these payloads.</p></div>
</div>

## Quick Decision Table

<table class="reference-matrix">
  <thead><tr><th>Boundary</th><th>Start with</th><th>Use when</th><th>Avoid first</th></tr></thead>
  <tbody>
    <tr><td>Local spatial math</td><td><code>Vector3</code>, <code>Quaternion</code>, <code>SE3Pose</code></td><td>The frame, unit, and source are already local context.</td><td>Stamped wrappers for values that never leave the local computation.</td></tr>
    <tr><td>Graph or process handoff</td><td><code>PoseStamped</code>, <code>TwistStamped</code>, <code>WrenchStamped</code></td><td>The value crosses a Flow, process, replay, dataset, or robot boundary.</td><td>Dropping <code>frame_id</code>, <code>stamp_ns</code>, or source before replay.</td></tr>
    <tr><td>Robot state</td><td><code>RobotState</code>, <code>JointState</code></td><td>A wrapper, monitor, policy, or simulator needs current robot configuration.</td><td>Unnamed joint arrays or opaque status strings.</td></tr>
    <tr><td>Scene and memory</td><td><code>WorldState</code>, <code>BeliefGraph</code></td><td>Perception, memory, grounding, and planning need a shared scene description.</td><td>Mixing geometric state, confidence, and task memory in one ad hoc dict.</td></tr>
    <tr><td>Planner handoff</td><td><code>TaskGoal</code>, <code>Skill</code>, <code>Plan</code>, <code>StructuredPlan</code></td><td>A planner or language module hands intent to a controller or monitor.</td><td>Passing natural-language instructions directly to control code.</td></tr>
    <tr><td>Motion and progress</td><td><code>Trajectory</code>, <code>ExecutionStatus</code></td><td>A controller or monitor reports timed motion, progress, terminal state, or errors.</td><td>Boolean-only success/failure with no progress or error context.</td></tr>
    <tr><td>Lightweight exchange</td><td><code>Action</code>, <code>Command</code>, <code>Status</code></td><td>A smoke demo, Hub export, or dataset bridge needs compact exchange records.</td><td>Embedding simulator/model-specific payloads in the public pack.</td></tr>
  </tbody>
</table>

## Common Choices

<div class="choice-grid">
  <div class="choice-card"><span>Geometry</span><strong>Pose, velocity, force</strong><p>Use <code>Vector3</code>, <code>Quaternion</code>, <code>SE3Pose</code>, <code>Twist</code>, and <code>Wrench</code> when a Flow only needs spatial values.</p></div>
  <div class="choice-card"><span>Stamped boundary</span><strong>Frame + time + source</strong><p>Use stamped wrappers when a value crosses a graph, process, dataset, or robot boundary.</p></div>
  <div class="choice-card"><span>World model</span><strong>Current robot and scene</strong><p>Use <code>RobotState</code>, <code>WorldState</code>, and <code>BeliefGraph</code> for perception, memory, planning, and monitoring examples.</p></div>
  <div class="choice-card"><span>Action layer</span><strong>Goal, skill, plan, trajectory</strong><p>Use <code>TaskGoal</code>, <code>Skill</code>, <code>Plan</code>, <code>StructuredPlan</code>, <code>Trajectory</code>, and <code>ExecutionStatus</code> for planner-to-controller handoff.</p></div>
</div>

## Authoring Pattern

Use direct imports inside example code. Use registry lookup at package boundaries: manifests, Hub packs, validation tools, replay readers, and dataset readers.

```python
from retriever_typing import PoseStamped, SE3Pose, get_type
from retriever_typing.robotics_types import WorldState, Plan, ExecutionStatus

pose_cls = get_type("PoseStamped")
assert pose_cls is PoseStamped
```

<div class="rule-grid">
  <div class="rule-card"><span>Authoring</span><strong>Prefer direct imports</strong><p>Code should be readable without asking the registry what every payload means.</p></div>
  <div class="rule-card"><span>Manifest</span><strong>Use registry lookup</strong><p>Hub packs and dataset readers can resolve names without importing optional robot integrations.</p></div>
  <div class="rule-card"><span>Boundary</span><strong>Validate before reuse</strong><p>Normalize frames, timestamps, quaternion norms, joint-array lengths, and progress ranges at graph edges.</p></div>
</div>

## Validation Checklist

<div class="rule-grid">
  <div class="rule-card"><span>Frames</span><strong>Keep frame IDs explicit</strong><p>Use non-empty <code>frame_id</code> when world, camera, robot, or object frames can be confused.</p></div>
  <div class="rule-card"><span>Time</span><strong>Preserve event time</strong><p>Keep <code>stamp_ns</code> monotonic per source when replay or event-time joins depend on ordering.</p></div>
  <div class="rule-card"><span>Motion</span><strong>Normalize rotations</strong><p>Check quaternion norms before a pose crosses into planners, controllers, or datasets.</p></div>
  <div class="rule-card"><span>Status</span><strong>Make progress comparable</strong><p>Keep <code>ExecutionStatus.progress</code> in <code>[0, 1]</code> so monitors and UI surfaces agree.</p></div>
</div>

<details class="reference-details">
  <summary>Detailed field reference for implementers</summary>
  <div>

<div class="type-grid type-grid-compact">
  <div class="type-card"><span>Vector3</span><strong>3D value</strong><p><code>x</code>, <code>y</code>, <code>z</code>. Use for positions, directions, velocities, forces, and offsets when the unit is declared by context.</p></div>
  <div class="type-card"><span>Quaternion</span><strong>Orientation</strong><p><code>x</code>, <code>y</code>, <code>z</code>, <code>w</code>. Normalize at boundaries; keep frame conventions outside the raw quaternion.</p></div>
  <div class="type-card"><span>SE3Pose</span><strong>Rigid pose</strong><p><code>position</code> plus <code>orientation</code>. Prefer this for object, end-effector, and robot poses.</p></div>
  <div class="type-card"><span>Twist</span><strong>Spatial velocity</strong><p><code>linear</code> plus <code>angular</code>. Use for velocity estimates or velocity commands.</p></div>
  <div class="type-card"><span>Wrench</span><strong>Force and torque</strong><p><code>force</code> plus <code>torque</code>. Use at contact, manipulation, or controller boundaries.</p></div>
  <div class="type-card"><span>JointState</span><strong>Joint arrays</strong><p><code>names</code>, <code>positions</code>, <code>velocities</code>, <code>efforts</code>. Arrays are aligned by index.</p></div>
  <div class="type-card"><span>Header</span><strong>Boundary metadata</strong><p><code>stamp_ns</code>, <code>frame_id</code>, <code>source</code>. Attach this before values leave a local Flow boundary.</p></div>
  <div class="type-card"><span>WorldState</span><strong>Scene state</strong><p>Current robot and object facts that perception, memory, and planning can share.</p></div>
  <div class="type-card"><span>BeliefGraph</span><strong>Probabilistic memory</strong><p>Symbolic scene memory and confidence values for grounding and planning.</p></div>
  <div class="type-card"><span>Skill / Plan</span><strong>Action vocabulary</strong><p>Named capabilities, parameters, and step sequences for planner-controller handoff.</p></div>
  <div class="type-card"><span>Trajectory</span><strong>Timed motion</strong><p>A time-indexed pose sequence for motion planning or control examples.</p></div>
  <div class="type-card"><span>ExecutionStatus</span><strong>Progress and terminal state</strong><p>Progress, status, and error text for monitors, controllers, and logs.</p></div>
</div>

  </div>
</details>

<div class="boundary-note">
<strong>Keep the base catalog small.</strong> Add covariance-bearing poses, richer frame graphs, or domain-specific schemas as separate Hub packs only after these base payloads are not enough.
</div>
